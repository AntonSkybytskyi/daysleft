### Stage 1 — AC compliance (blocking) → routed to implement

1. **[T60, BLOCKING]** AC-02b's outcome still isn't delivered, on either device.
   `SsoCallbackContainer.tsx:46,78` route both `onVerifiedOnOtherDevice` and
   `EmailLinkErrorCodeStatus.ClientMismatch` to `MagicLinkInvalidScreen` ("This link is no longer
   valid" — `MagicLinkInvalidScreen.tsx:15-16,44`), which is false: per Clerk's own semantics
   (`@clerk/shared@4.30.2`'s type doc, confirmed against the installed package),
   `onVerifiedOnOtherDevice` fires precisely when verification *succeeded* on the other device.
   `spec.md:104-108` (AC-02b), `sad.md:192-217` (flow 3's second branch), and `ux-flows.md:55,128`
   all specify session-established-and-dashboard-shown on the device that opened the link.
   Compounding it: the error screen's sole CTA calls `signIn.create({ strategy: "email_link" })`
   (`SsoCallbackContainer.tsx:104`), a **new** sign-in attempt that supersedes the session just
   established on the other device — the offered recovery action can destroy the very success
   it's misreporting as a failure.

   The other half of the gap: nothing polls on the *originating* device either.
   `grep -rn "createEmailLinkFlow|startEmailLinkFlow" src/ e2e/` returns zero hits;
   `CheckEmailContainer.tsx:23-55` has no `useEffect`, no subscription, no navigation-on-success —
   only a manual Resend button. So in the concrete scenario this AC exists for (request a link on
   your phone, open it on your laptop), the laptop sees a false "link is no longer valid" error,
   the phone sits on "check your email" forever, and the sign-in completes on neither device.
   Requesting and opening a *second* link on the same device works, which is why this is easy to
   miss in manual testing.

   Both `SsoCallbackContainer.test.tsx:109-123,249-267` assert the deviation as correct, with a
   test name arguing the case for it. `test-plan.md:36`'s single planned test level for AC-02b
   (e2e-through-UI) was never written — `e2e/auth-dashboard.spec.ts` has no AC-02b scenario at
   all, not even a skipped one (this is distinct from the deferred spec.md §8 item, which covers
   *existing* scenarios not executing without a live Clerk instance). No artifact records the
   deviation: spec.md §8 has no entry, and ADR-0001's Consequences section doesn't mention that
   Clerk's email-link model can't deliver AC-02b as shipped.

   **Resolved direction:** implement Clerk's `startEmailLinkFlow` polling on `/check-email` so the
   originating device completes the sign-in and navigates to the dashboard once Clerk reports
   verified, keeping AC-02b's current wording; give the second device a truthful
   "verified-on-other-device" state with no destructive resend CTA; update screens.md, test-plan.md,
   and ADR-0001's Consequences to match; rewrite both tests to assert the decided outcome. AC-02b.

### Stage 2 — quality / regressions introduced by this round's own fixes → routed to implement

2. **[T61]** T54's fix has an unhandled edge case: if the server logout returns 204 (session
   revoked) but the client-side `clerk.signOut()` call then rejects (e.g. a network blip),
   `DashboardContainer.tsx:65-69` shows "Couldn't sign you out. You're still signed in — try
   again." Retrying re-POSTs `/api/v1/auth/logout`, which now 401s (`logout.ts:12-14`, no server
   session left) since the server side already succeeded — so the same unactionable error repeats
   indefinitely while the user still holds a live client JWT and can still reach the dashboard.
   No test covers `signOut()` rejecting. AC-06.
3. **[T62]** T55's persistence fix introduced a durability-without-invalidation gap: nothing
   updates or deletes a `linked_identities` row once written — `session.ts:34-40` dropped the old
   delete-on-conflict path, and `link()` (`onConflictDoNothing`) is the only writer anywhere in
   the codebase. If a Clerk identity's email later changes, the stale identity→user mapping is
   now permanent — previously the in-process `Map` at least self-healed on restart; persisting it
   makes the wrong answer durable instead of the old (worse in other ways, but self-correcting)
   behavior. AC-03.
4. **[T63, minor]** AC-03's UI chain is proven at both ends but never joined:
   `DashboardContainer.tsx:39,72` wires the API's `linked` field to the "signed in to your
   existing account" banner, but every `DashboardContainer.test.tsx` fetch fixture omits `linked`,
   so a rename or a dropped prop would go undetected while `DashboardScreen.test.tsx` (banner
   given the prop) and the backend integration tests (mapping resolves correctly) both stay green
   in isolation. This feature's recurring defect shape across four rounds is exactly "both ends
   green, the connection dead." AC-03.
5. **[T64, minor/low]** Two small items batched: `screens.md:97`'s SCR-02 `error-sign-in-failed`
   row cites AC-02b for what is actually an AC-02 case (resend failure on the check-email screen,
   not cross-device) — the parallel SCR-04 row correctly cites AC-02 for the same situation, and
   this mis-citation is currently the only "AC-02b" string in the manifest, making the AC look
   covered when it isn't. Separately, `scripts/migrate-down.ts:42-44`'s journal-row `DELETE` went
   from parameterized (`postgres.js` template literal) to string-interpolated during T59's
   extraction into `deleteJournalRowSql`; input is repo-controlled (low severity) but the
   extraction didn't need to give up parameterization.

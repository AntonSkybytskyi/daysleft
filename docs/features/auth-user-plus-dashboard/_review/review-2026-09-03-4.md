### Stage 1 — AC compliance (blocking) → routed to implement

1. **[T60]** AC-02b's outcome still isn't delivered. `SsoCallbackContainer.tsx:46,78` route both
   `onVerifiedOnOtherDevice` and `EmailLinkErrorCodeStatus.ClientMismatch` to
   `MagicLinkInvalidScreen` ("This link is no longer valid"; `MagicLinkInvalidScreen.tsx:15-16,44`)
   — but per `@clerk/shared`'s own semantics (confirmed against the installed package's type
   doc), `onVerifiedOnOtherDevice` fires precisely when verification *succeeded* on the other
   device. `spec.md:104-108` (AC-02b), `sad.md:192-217` (flow 3's second branch), and
   `ux-flows.md:55,128` all specify: session established on the device that opened the link, that
   device shows the dashboard directly. What ships is the AC-02 **error** screen instead — a
   Traveler who requests a link on their phone and opens it on their laptop sees "send a new
   link" on the laptop, and the AC's stated scenario is unreachable by design.
   Compounding this: that screen's sole CTA calls `signIn.create({ strategy: "email_link" })`
   (`SsoCallbackContainer.tsx:104`), creating a **new** sign-in attempt that supersedes the
   session just established on the other device — the offered recovery action can destroy the
   very success it's misreporting as a failure. AC-02b.

### Stage 2 — quality / regressions introduced by this round's own fixes → routed to implement

2. **[T61]** T54's fix has an unhandled edge case: if the server logout returns 204 (session
   revoked) but the client-side `clerk.signOut()` call then rejects (e.g. a network blip),
   `DashboardContainer.tsx:65-69` shows "Couldn't sign you out. You're still signed in — try
   again." Retrying re-POSTs `/api/v1/auth/logout`, which now 401s (`logout.ts:12-14`, no server
   session left) since the server side already succeeded — so the same unactionable error repeats
   indefinitely while the user still holds a live client JWT and can still reach the dashboard.
   No test covers `signOut()` rejecting. AC-06.
3. **[T62]** T55's persistence fix introduced a durability-without-invalidation gap: nothing
   updates or deletes a `linked_identities` row once written — `session.ts:34-40` dropped the old
   delete-on-conflict path, and `link()` (`onConflictDoNothing`) is the only writer anywhere in
   the codebase. If a Clerk identity's email later changes, the stale identity→user mapping is
   now permanent — previously the in-process `Map` at least self-healed on restart; persisting it
   makes the wrong answer durable instead. AC-03.

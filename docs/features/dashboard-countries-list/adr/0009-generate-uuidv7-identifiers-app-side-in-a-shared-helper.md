# 0009 — Generate UUIDv7 identifiers app-side in a shared helper

- **Status:** Accepted
- **Date:** 2026-09-06
- **Deciders:** Tech Lead (during the `design` Socratic walk)

## Context

`CLAUDE.md` and `docs/architecture-map.md` both state app-side UUIDv7 as the project's ID convention, but no identifier has ever been generated by this application: `users.id` and `linked_identities.identity_id` are Clerk's identifiers, stored as text. `tracked_destinations` is the first table whose rows the app itself creates, so this feature materializes the convention and creates the shared helper every later feature will use. Two acceptance criteria bear on the choice: AC-03 uses each record's own identifier to settle ordering ties, and §6.1 names enumeration through the identifier exposed in a saved address as an abuse case.

## Decision drivers

- `CLAUDE.md` and SAD §2 Conventions: UUIDv7 generated app-side, time-sortable.
- Spec §5 AC-03: records in recorded order, most recent last, with the identifier settling ties so two added moments apart never swap places.
- Spec §6.1: the identifier is exposed in a shareable address, and enumeration is a named abuse case.
- Spec §8: offline creation is deferred but expected, and app-side generation is what lets an offline-created record keep its identity on sync.

## Considered options

1. **UUIDv7**, generated app-side by a new `src/lib/id.ts`.
2. **Random UUIDv4**, generated app-side.
3. **UUIDv7 primary key plus a separate random public identifier** used in the address.

## Decision outcome

**Chosen:** Option 1. It is the convention already written down, and it is the one that makes AC-03's tie-break meaningful rather than arbitrary — a UUIDv7 tie-break agrees with recorded order, whereas a UUIDv4 tie-break is a stable but meaningless lexical comparison. Its 74 random bits put guessing out of reach, so the §6.1 enumeration case is answered by the identifier's entropy as well as by ADR-0008's uniform response. Option 3 closes a real but narrow leak — the embedded creation timestamp — at the cost of a second column, a second unique index and two identities per record, which is not worth it when the only party who holds the URL is the record's owner.

## Decision drivers accepted as residual risk

The identifier embeds a millisecond creation timestamp. Anyone holding a saved address therefore learns when that tracked destination was created. Today that is the owner, or someone the owner shared the address with; it discloses nothing the address itself does not already disclose. Recorded in SAD §11.

## Consequences

**Positive**
- Satisfies the stated project convention on its first real use, and creates the helper every later feature inherits.
- Ordering ties resolve consistently with recorded order, which is exactly what AC-03 asks for.
- App-side generation is what a future offline-created record needs in order to keep its identity through a sync.

**Negative**
- The identifier discloses its creation time to whoever holds it.
- Adds a dependency or a small hand-written generator in `src/lib/id.ts`; either way it needs a test that the output is a valid, monotonically increasing v7.

**Neutral**
- Changing to Option 2 later would need a backfill and would invalidate every saved address; changing to Option 3 later is additive and would not.
